# Weekly Attendance-Risk Model (AI/ML Pod — ATT)

Predicts whether a student's attendance will be **low next week**, per
section, using weekly features prepared by the Data Analyst pod.

## Input

- File: `demo_data/weekly_features_and_flags.xlsx`
- Sheet: `WeeklyFeaturesAndFlags`
- Produced by: Data Analyst pod (not generated by this script)
- Required columns: `attendance_rate_to_date`, `trend_last_3`,
  `rejected_last_2`, `consecutive_absences`, `course_load`,
  `label_next_week_low`, `flag_any`

> If the Data Analyst renames a column or changes the file path, this
> script will break — confirm any changes with them first.

## How to run

```
pip install pandas numpy scikit-learn openpyxl
python train_weekly_risk_model.py
```

## What it does

1. Loads the weekly feature table and drops rows with no next-week label
   or missing features.
2. Splits into train/test (75%/25%, stratified, `random_state=42`).
3. Trains a Logistic Regression (`class_weight="balanced"`) to predict
   `label_next_week_low`.
4. Reports precision/recall/F1/Brier score for both the model and the
   rule-based baseline (`flag_any`), on the same test rows, for a fair
   comparison.
5. Prints model coefficients and a calibration table (predicted risk band
   vs. actual observed rate).

## Results (on the demo dataset)

| Metric | Baseline (rule-based) | Logistic Regression |
|---|---|---|
| Precision | 0.251 | 0.220 |
| Recall | 0.532 | 0.620 |
| F1 | 0.341 | 0.325 |
| Brier score | — | 0.183 |

- Rows used: 2,950 (train: 2,212 / test: 738)
- Positive rate (true low-attendance cases): 10.7%

**Verdict:** the model does not clearly beat the baseline — it trades
precision for recall, and F1 is essentially tied. Per the project's AI
release gate, this is a valid, documented result. See the full report
(`ATT_AI_ML_Report.md`) for limitations, model/version log, and fallback
plan.

## Fallback

If this model is unavailable, the system falls back to the deterministic
rule-based baseline (`flag_any`, already present in the input file) — no
attendance-capture flow depends on this model being available.

## API

The model is served via `weekly_risk_api.py` (FastAPI):

- `POST /predict-weekly-risk` — requires `X-Service-Key` header. Takes
  `attendance_rate_to_date`, `trend_last_3`, `rejected_last_2`,
  `consecutive_absences`, `course_load` and returns `risk_probability`,
  `risk_band`, `is_flagged`, `source` (`"model"` or `"baseline_fallback"`).
- `GET /health` — public, returns `{"status": "ok"}` only.
- `GET /admin/model-status` — requires `X-Service-Key`, returns
  `model_loaded`.

Run with:
```
pip install fastapi uvicorn joblib slowapi
uvicorn weekly_risk_api:app --reload --port 8000
```
Interactive docs at `http://127.0.0.1:8000/docs`.

## Security fixes (per security review)

| # | Finding | Fix | Verified |
|---|---|---|---|
| 1 | No auth on prediction endpoint | `X-Service-Key` header required | ✅ `curl` without key → 401, with key → 200 |
| 2 | Unsafe pickle loading, no integrity check | SHA256 hash written at training, checked before load | ✅ tampered model file → refused, fallback used |
| 3 | No rate limiting | `slowapi`, 20 req/min per IP on `/predict-weekly-risk` | ✅ 25 rapid requests → 20×200, 5×429 |
| 4 | `/health` leaked model-loaded state, unauthenticated | Simplified `/health`; moved detail to authenticated `/admin/model-status` | ✅ |
| 5 | Fixed, guessable fallback probabilities (0.8/0.1) | Graded score from rule severity instead of two constants | ✅ different inputs → different fallback probabilities |
| 6 | Overly broad exception handling | Input errors (`ValueError`/`TypeError`) logged separately from unexpected errors | ✅ |

## Graceful Degradation — tested manually

Verified on 2026-09-20 via `/docs`:

1. Sent a request with the model file (`weekly_risk_model.joblib`) in
   place → response returned `"source": "model"` with a real predicted
   probability (0.877 for a low-attendance/declining-trend student).
2. Renamed the model file to simulate it being unavailable, restarted the
   API, sent the exact same request → response returned
   `"source": "baseline_fallback"` with the deterministic rule's output
   (0.8 probability, correctly flagged) instead of an error.
3. Restored the model file afterward so the API resumes using the real
   model.

**Result:** the API never fails or blocks the caller when the model is
unavailable — it degrades to the rule-based baseline automatically, as
required by the project's AI release gate.
